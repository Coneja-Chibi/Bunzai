Reasoning block, one surface, five looks

A new theme surface, scene.reasoning. The host builds the variants; a theme manifest only picks one. Behaviour never changes between columns: two separate blocks on a reply (native reasoning first, then the think-tag block), "Reasoned for N s" and "Thought for N s", collapsed by default, open while streaming, the two settings. Every column shows the pair on one reply, collapsed then open, in that theme's own palette. Click a header to toggle it. Default first: RoleCall's own design with the glass taken out. Then the four shipped themes, each with the look that fits its identity.

Role colours, same in every column. info marks the model's own reasoning channel (native): it arrives from the provider, outside the story text. select marks thinking the model wrote inside the reply and the app picked out by its tags. The default also uses the character's tone, as RoleCall does. Warn and danger stay free for finish reasons and failures. In every variant the two blocks differ by structure as well as hue: rule weight, solid versus dashed, filled versus outlined label, mono versus italic serif body.

Steps

  1. Add "scene.reasoning": ["program-note", "slot-tab", "slab-note", "footnote"] to src/extensions/surface-registry.ts, in the order Theater, Encore, GirliePop, Paper. The comment there already says a variant not built renders as core.
  2. Create the variant folder src/ui/apps/scenes/variants/scene.reasoning/ (match the existing folder naming in that directory), one file per variant: program-note, slot-tab, slab-note, footnote, plus the core rendering in the surface itself. surface-registry.test.ts fails if a folder names an id that is missing from the registry.
  3. One logic module: splitReasoning (beside stripReasoningTags), open state, durations and the two settings (scenes.autoOpenReasoning, scenes.capLongReasoning) live once. Variants differ in markup and CSS only, never in data handling.
  4. Read the variant with useSurfaceVariant("scene.reasoning"), as scene-meta.tsx and scene-page.tsx do for their surfaces. The painter already writes data-surface-scene-reasoning.
  5. Add the picks to the four bundled manifests: theater: program-note; stage (GirliePop): slab-note; paper: footnote; and to the Encore example (src/extensions/examples/bunraku.theme.encore/manifest.json): slot-tab. greenroom names none, so it renders core. Run scripts/wireframe-theme.ts if palettes change, and the theme-difference test: it counts this surface.
  6. Keep every variant to the same anatomy: label, duration, snippet (collapsed), copy and toggle in the header, body when open; native first. Native label "Backstage - Native Reasoning", tag label "Behind the Scene"; durations "Reasoned for" and "Thought for". Square corners, 12px floor, tokens only, no blur, glow, gradient or translucent fill, and a contrast check in all five palettes (the same check the other variants carry).
  7. Render tests per variant (all parts present, native before tags, hidden when empty), a keyboard and focus check on the header button, and screenshots in the four themes.

Parts a mod can target (data-part names)

Names must be added to the generated parts page the way the other parts are (a mod stylesheet may only aim at parts that exist).

  • reasoning-block on the block root, with data-kind="native" or data-kind="tags" and data-open="true|false"
  • reasoning-header (the toggle button), reasoning-icon, reasoning-label, reasoning-number, reasoning-duration, reasoning-snippet, reasoning-copy, reasoning-chevron
  • reasoning-body, and reasoning-curtain (the "Before the curtain" line, core native only)

The markup in this wireframe already carries these names as data-part attributes.
